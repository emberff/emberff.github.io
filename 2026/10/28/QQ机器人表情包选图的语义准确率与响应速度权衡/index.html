QQ机器人表情包选图的语义准确率与响应速度权衡

给 QQ 机器人加表情包功能之后，遇到了一个典型的工程权衡：模型能判断”该不该发表情”，却只能指定”哪一类”，具体发哪一张全靠随机。要让选图也懂语义，最直接的做法是让 LLM 再做一次选择——实测多花 4.2 秒。本文记录如何在不牺牲响应速度的前提下拿到语义选图，以及最终方案为什么是”保留旧模式的快速路径，只把分类内随机换成分类内按 caption 相似度选”。

一、环境与问题

1.1 运行环境

本文所有实测数据来自下面这套真实部署，不是本地模拟：

项目配置
机器人框架AstrBot（soulter/astrbot:latest，Docker 部署）
QQ 协议端snowluma（motricseven7/snowluma:latest）

1.2 表情包的两种工作模式

表情感知插件在关闭 LLM 辅助（generation.emotion.llm.enabled = false）时走的是标记解析路径：

flowchart LR
    A[模型生成回复] --> B["回复文本含 &&sigh&& 标记"]
    B --> C[解析器提取分类名]
    C --> D["从 sigh 目录 18 张图中 random.choice"]
    D --> E[附加图片发送]

模型输出的是分类键（sigh / happy / angry 等 20 个），不是具体图片。插件拿到分类后：

分类判断是准的，但同一分类内的 18 张图等概率随机——可能模型表达的是”无奈地叹气”，随机抽到的却是”翻白眼嘲讽”。

1.3 为什么不能直接开 LLM 语义选图

插件本身支持语义模式（emotion.llm.enabled = true），流程变成两次额外的 LLM 调用：

环节内容实测耗时
主回复生成聊天内容2.3 s
检索词生成把回复压成 11 字检索短语2.5 s
表情选择从候选里挑具体表情 ID1.7 s
消息发送QQ 侧2.1 s
合计约 11 s

主回复只要 2.3 秒，表情包相关占了 4.2 秒。更尴尬的是，实测某次表情选择返回 []——模型判断”没有合适的”，4.2 秒白花。

一个反直觉的细节：原实现是每次都跑两次 LLM，最后才按概率决定加不加图。也就是说大部分请求白花了 4.2 秒，只为了得到”这次不发表情”的结论。

2.2 三个方案的延迟预算

先量一下各环节的真实成本，再决定在哪插语义：

环节实测延迟说明
embedding API（SiliconFlow bge-m3，1024 维）110 ms5 次采样 106–149 ms
FAISS 检索（398 张，IndexFlatIP）0.78 ms中位数，最大 1.68 ms
索引加载8 ms只需一次，插件内有缓存
分类子集向量重建（18 张）< 1 msindex.reconstruct()
语义选图合计约 111 ms相比 11 秒总耗时占 1%

对照表一目了然：

方案额外延迟选图准确率
分类内随机（原状）0 ms分类对，图随机
分类内语义选（本文方案）+111 ms分类对，图贴切
LLM 全量语义选+4200 ms分类对，图贴切

111 ms 比 4200 ms 快 38 倍，而两者在”图是否贴切”上的效果是同级的。 这个差距直接决定了方案选择。

三、方案：只替换最后一步的选图逻辑

3.1 设计原则

不动分类判断，只动”同分类内选哪张”：

flowchart TB
    A[模型生成回复] --> B["&&sigh&& 标记"]
    B --> C[解析器提取分类]
    C --> D{语义选图}
    D -->|成功 111ms| E[按 caption 相似度选中的图]
    D -->|失败/异常| F[random.choice 兜底]
    E --> G[发送]
    F --> G

三条硬约束：

  1. 不改变分类判断 —— 模型仍然只说”哪一类”，语义只用于类内精排
  2. 失败必须降级 —— 任何环节异常都回退 random.choice，功能不能退化
  3. 不加新依赖 —— 复用插件已有的 EmbeddingAdapter、_read_faiss_index、load_metadata

3.2 关键坑：全库检索再过滤分类，行不通

第一版实现走的是最直观的路：全库检索 top-20，然后过滤出目标分类的条目。

实测直接失败：

全库 top-20 里一张 sigh 分类的图都没有——398 张图分散在 20 个分类，某单一分类平均只占 20 张，语义相近的其他分类（sad / confused）会把名额挤满。

这个失败很有教育意义：向量检索的 top-K 是全局排序，不是”每个分类各取 K 个”。任何”先全库检索再按属性过滤”的写法，都会在属性分布不均时静默返回空。

3.3 正确做法：在分类子集内建临时索引

FAISS 的 IndexFlatIP 支持按 ID 取回向量，于是可以先把目标分类的向量抽出来建子索引：

reconstruct() 重建 18 条向量的实测耗时是 0.0 ms（可忽略），子集检索 0.72 ms。所以完全不需要缓存子索引——每次重建反而避免了”索引更新后缓存失效”的一致性问题。

六、为什么最终选了这条路

6.1 三种模式的完整对比

维度分类内随机分类内语义选LLM 全量语义选
额外延迟0 ms111 ms4200 ms
分类准确率模型决定模型决定（不变）模型决定
选图准确率随机按 caption 相似度按 caption 相似度
依赖 LLM 配额否否是（每次 2 次调用）
失败影响无降级到随机表情功能整体失效
可观测性无日志有 score 日志有
实现复杂度—约 120 行0（插件原生）

6.2 三个决定性理由

理由一：延迟预算的边际收益是断崖式的。 从 4200ms 降到 111ms，用户感知从”明显卡顿”变成”完全无感”；而从 111ms 再降到 0ms，用户感知没有任何变化。优化到感知阈值以下就应该停手。

理由二：不引入新的失败面。 LLM 语义选图多两次网络调用，多两个可能超时/限流/返回非法 JSON 的点。语义选图只依赖一次 embedding，而且失败了自动降级——最坏情况退化成原方案，不会更差。

理由三：分类和选图是两个不同粒度的决策，应该分开优化。 分类（该不该发、发哪类）需要理解上下文，是 LLM 的强项；选图（同类里哪张最贴切）是纯语义匹配，向量检索就够了。让 LLM 做它擅长的那一半，让向量检索做它擅长的另一半。

6.3 一个诚实的局限

分类内语义选图的准确率上限被分类质量锁死：如果模型把”无奈”判成了 angry，那么再精准的类内选图也只是”选了一张最像无奈的 angry 图”。

实测中确实遇到过：模型对”微笑表情包”的请求输出了 &&happy&&，而当时角色状态是”口渴烦躁”——语义选图在这个 happy 子集里选出的图，与角色真实情绪的匹配度受限于分类本身。

要进一步优化，得从分类粒度入手（增加分类、或让模型输出更细的语义标签），而不是继续优化选图。 这是下一阶段的事。

七、经验总结

经验说明
先量延迟预算再选方案110ms vs 4200ms 的差距是在写代码前测出来的，不是猜的
复用已有基础设施插件早有 FAISS 索引和 caption，缺的只是调用位置
top-K 检索不能当”按分类过滤”用全局排序会饿死小分类，必须在子集内检索
语义功能的验收要断言确定性两次相同输入选不同图 = 根本没走检索
降级路径是功能的一部分return None + random.choice 兜底，让优化可以随时回滚
跨函数作用域传参先确认变量存在clean_text 的 NameError 让整个装饰阶段静默失败

回头看，这次优化真正的价值不在于”用了向量检索”，而在于先算清了延迟预算，再选择在哪一步插进去。如果一开始就照着”语义化”的字面意思去做 LLM 二次选择，会得到一个慢 4 秒、且失败率更高的方案——技术上正确，工程上错误。
