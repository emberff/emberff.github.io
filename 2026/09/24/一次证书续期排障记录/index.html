一次 Let's Encrypt 证书全量续期与自动续期排障记录

起因只是一句”服务器上的自签证书过期了，怎么续期？”，结果越查越大：11 张 Let’s Encrypt 证书其实全都过期了，续期途中又撞上通配符证书的手动验证、权威 DNS 不在你以为的那家云、自定义 Nginx 的 PID 文件对不上、以及一个被 Markdown 代码围栏污染的续期脚本。本文按 起因 → 定位 → 解决 → 验证 的顺序把整个过程复盘一遍，最后给出一套可以直接用的自动续期方案。

一、背景与初始问题

先把环境交代清楚，本次所有坑几乎都和这套”非标准”环境有关：

项目值
系统CentOS 8.5 (2111)
Python3.6.8
pip9.0.3
Certbot1.22.0（/usr/bin/certbot，pip 安装）
Nginx自定义编译版 /usr/local/nginx/sbin/nginx
域名hopai.cn 及其一批子域名

最开始的问题是：用 OpenSSL 自己生成的自签名证书过期了，怎么”续期”？

这里必须先把概念掰正：

自签名证书没有”续期”这个说法。 它不像 Let’s Encrypt 那样有 ACME 协议可以复用原有 lineage 重新签发，所谓”续期”本质上就是重新生成一张新的自签名证书。

OpenSSL 的 req -x509 可以直接生成自签名证书，用 -days 指定有效期。

1.1 分情况重新生成自签名证书

情况 A：原私钥还在（推荐，可继续沿用原私钥）

情况 B：连原私钥也没了，直接连私钥一起重新生成

1.2 一个容易被忽略的关键点：subjectAltName

如果证书要支持多个域名，只有 CN 是不够的。现代浏览器（Chrome 58+ 起）早已不再回退到 CN 匹配，必须带上 subjectAltName，否则浏览器照样判定”证书与域名不匹配”。

三、全量续期：先看配置，别急着重签

3.1 明确”不要做”的事

  • ❌ 不要 rm -rf /etc/letsencrypt/...：这会把证书续期链（lineage）和配置一起搞乱。
  • ❌ 不要上来就 certbot certonly 重建一堆新证书：容易和现有的 11 个 lineage 打架。
  • ❌ 不要一上来就全量 certbot renew：先单张验证，确认验证方式可用再批量。

五、想让通配符自动续期：踩了”权威 DNS 不在阿里云”的坑

既然 manual 每 90 天都要人工加 TXT，长期方案自然是换成 DNS API 插件自动续期。

5.1 版本兼容是第一道坎

Certbot 1.22.0 + Python 3.6.8 这个组合比较老，不能直接装最新插件（新版 certbot-dns-aliyun 要求 certbot>=2.0.0）。旧版 0.38.1 明确支持 Python 3.6：

输出里有两个问题：

第一个好办（chmod 600 + chown root:root）。第二个才是关键 —— 插件明明调用阿里云 API 成功创建了 TXT 记录，为什么 Let’s Encrypt 还查不到正确的值？

因为你要查”谁是权威 DNS”，而不是”DNS 记录加在哪家云控制台”。

结果：

hopai.cn 的权威 DNS 是 Cloudflare，不是阿里云。

所以 dns-aliyun 插件虽然成功调用了阿里云 API 写入了 TXT 记录，但那不是公网权威记录。Let’s Encrypt 最终查询的是 Cloudflare 上的 _acme-challenge.hopai.cn，自然只能看到一个”旧的、不匹配的” TXT 值，于是报 Incorrect TXT record。

正确的组合应该是 certbot-dns-cloudflare + Cloudflare API Token（Token 权限限制到具体 Zone 的 DNS:Edit），凭据存到 /root/.secrets/certbot/cloudflare.ini。

这次踩坑的经验：DNS-01 验证失败时，第一件事永远是 dig NS <域名> 确认权威 DNS 到底是哪家，不要想当然以为 DNS 托管在你配 API 的那家云。

好在这次绕的弯路没有副作用：阿里云的 RAM 用户和 AccessKey 只是”对这张证书没用”，本身不产生任何影响，先留着即可。

6.1 先把旧任务找出来

用户提到”以前写过自动续期脚本，但可能没设置 Nginx 启停所以失败”。与其重写，不如先找旧的：

6.2 方案设计要点

  1. standalone 证书续期时必须释放 80 端口 → 必须先停 Nginx，续完再拉起；
  2. Nginx 不是 systemd 管理的，不能用 systemctl stop nginx；
  3. 不管 Certbot 成功还是失败，都必须把 Nginx 恢复起来（用 trap）；
  4. 加文件锁，避免定时任务重入；
  5. 启动前先 nginx -t 校验配置，避免配置错误导致 Nginx 起不来；
  6. 输出全部写日志，方便事后排查。

七、排障实录：脚本为什么跑不起来

脚本写完了，但真正跑起来又是一路踩坑，这一节反而是最有价值的部分。

7.1 坑一：nginx -s stop 报 PID 文件不存在

日志里出现：

但从 pgrep nginx 看，Nginx 明明活得好好的。这就很矛盾：进程在，PID 文件却不在。

排查：

结果真相大白：

实际运行的 Nginx 是用 /etc/nginx/nginx.conf 启动的，而不是我们脚本假定的 /usr/local/nginx/conf/nginx.conf！

这就解释了一切：

  • nginx -s stop 按 /usr/local/nginx/conf/nginx.conf 去找 PID 文件 → 找不到 → 报错；
  • 日志里那些 /etc/nginx/conf.d/katenest.hopai.cn.conf 之类的 warning 也顺理成章了。

顺带澄清一个概念：进程 PID 和 PID 文件是两回事。 进程 PID 每次启动都由内核分配，每次都会变；而 PID 文件路径是固定的（如 /usr/local/nginx/logs/nginx.pid），文件里记录”当前这次 master 进程的 PID”。所以脚本里绝不能写死某个 PID，而应该每次去读 PID 文件。

解决：让 /usr/local 这套 Nginx 接管。 关键是先测试再动手，避免中途服务不可用：

八、验证定时任务是否真的会执行

用户提出要写个测试脚本：查看证书过期时间 → 把 cron 改到 5 分钟后 → 再查 → 恢复原时间。

这里有个认知很重要：

certbot renew 只有在证书进入续期窗口时才会真正更新证书。所以”5 分钟后证书过期时间没变”是正常现象，不能据此判断定时任务失败。

判断定时任务是否生效的正确标准是：/var/log/certbot-renew.log 里有没有出现新的执行记录。

于是测试脚本 /usr/local/sbin/test-certbot-cron.sh 的核心逻辑是：

  1. 备份原 cron 文件；
  2. 把执行时间临时改成”5 分钟后”；
  3. 等到目标时间并等待 cron 触发；
  4. 用 awk 找出时间戳晚于测试开始时刻的 Certbot renewal started 记录（避免把上一次的日志误判为本次）；
  5. 检查是否有 Certbot renewal finished.；
  6. 恢复原 cron 并输出明确的 RESULT: CRON TEST PASSED / FAILED。

#现象根因解决
1自签名证书”续期”概念错误，自签名无续期一说用 openssl req -x509 重新生成，并带 -addext subjectAltName
211 张证书全部过期旧的自动续期任务已消失先手动 certbot renew 恢复，再重建自动续期
3部分证书续期失败authenticator 方式不同（standalone 需停 Nginx）先看 renewal 配置，再决定是否停服务
4hopai.cn 通配符续不掉manual + DNS-01 缺少 manual-auth-hook手动加 TXT 续期，长期改用 DNS API 插件
5katenest.hopai.cn 404webroot 目录与 Nginx 实际目录不一致对齐 webroot_path 与 location
6DNS-01 报 Incorrect TXT record权威 DNS 在 Cloudflare，插件写到了阿里云dig NS 确认权威 DNS，换对应的插件
7nginx -s stop 报找不到 PID 文件实际运行的 Nginx 用的是 /etc/nginx/nginx.conf明确 Nginx 启动方式与 PID 文件位置
8脚本执行了却不写日志文件首行混进了 Markdown 代码围栏 ```bashsed 删除首尾围栏，用 xxd 确认文件头

除了技术问题，这次还踩了一堆命令行使用上的低级坑，但都很真实，一并记下：

  • 反斜杠后面多了个空格：\ 不是续行符，导致整条被拆成多个参数，Certbot 直接打印 usage。要用 \⏎，不是 \ ⏎。
  • heredoc 的 EOF 和内容写在同一行：卡在 heredoc> 提示符里，EOF 必须独占一行。
  • 把示例输出当命令粘贴：比如把 -rw-r--r-- 1 root root ... 这行提示当成命令执行，得到 command not found。
  • 多条命令写一行：which certbot certbot --version ... 会被 which 当成多个要查找的命令名；bash -n script echo $? 里 echo $? 会被当成参数。

后续可优化项

  1. 把通配符证书切到 certbot-dns-cloudflare，凭据放 /root/.secrets/certbot/cloudflare.ini 并 chmod 600，API Token 只授予 hopai.cn 这个 Zone 的 DNS:Edit。
  2. 改用 --pre-hook / --post-hook 替代”每天无条件停 Nginx”：Certbot 的 hook 只在确实有证书需要续期时才执行，这样正常情况下不会产生任何服务中断。你现在的 Nginx 不是 systemd 管理的，所以 hook 里要写 /usr/local/nginx/sbin/nginx -s stop 而不是 systemctl stop nginx。
  3. 顺手修掉 katenest.hopai.cn 的 webroot 路径，让 11 张证书全部进入自动续期。
  4. 清理 _acme-challenge 下的历史 TXT 记录前，先确认没有其他服务依赖它。
