AstrBot 群聊机器人：变慢归因与消息丢失修复

起因是一句话：”分析从昨天到现在的聊天记录，分析 bot 今天的回复速度显著变慢的原因。”

结果查下来，体感和数据并不一致：今天真正慢的幅度只有 7%–13%，而我在过程中先后做错了三次判断——以为中转挂了、以为上下文膨胀是主因、以为决策 AI 塞了 100 条历史。三次都被数据推翻之后，才找到两个真正的问题：被概率筛掉的消息会永久丢失，以及一次 4 秒的 LLM 摘要卡在用户可见的关键路径上。

本文按 原因 → 目的 → 修改方式评估 → 修改后效果 复盘一遍，也把被否掉的方案一起记下来，方便以后不再踩。

一、起因与环境

1.1 问题描述

用户观察到”bot 今天回复明显变慢”，要求分析从昨天到现在的聊天记录。随后追加了两个问题：被概率筛掉的消息会不会丢、能不能把串行的 LLM 调用改成并行。

1.2 环境

本次排查涉及的技术栈如下，后文的结论都建立在具体版本上：

项目版本 / 说明
聊天机器人框架AstrBot 4.29.3
群聊增强插件astrbot_plugin_group_chat_plus V1.2.3.hotfix.2
角色状态插件astrbot_plugin_LivelyState v1.2.1
长期记忆插件astrbot_plugin_livingmemory
运行时Python 3 / asyncio（单事件循环）
模型上游OpenAI 兼容协议的网关，DeepSeek 系模型（流式）
存储SQLite（data_v4.db，WAL 模式）
部署Docker + 单容器 astrbot
本文博客框架Hexo 8.1.2 + hexo-theme-fluid 1.9.9

1.3 可用数据

排查没有靠猜，全部落在两张表与一份容器日志上：

数据源关键字段用途
provider_stats 表start_time / end_time / time_to_first_token / token 三项精确算 LLM 耗时与首 token
platform_message_history 表created_at / user_id / content算端到端延迟、查历史是否落库
docker logs astrbot10 万行，覆盖 39 小时分段耗时、阶段标记、异常

两个容易踩的时间坑：created_at 存的是 UTC，要 +8 才是本地时间；而 provider_stats.start_time 是秒级浮点 epoch（不是毫秒）。混用时差一小时或差一千倍，结论会完全走偏。

二、原因：三次定位，两次推翻自己

2.1 第一次误判：以为今天慢了

初始假设很自然：是不是模型中转链路挂了，导致每次请求先超时再降级到官方 API。

实测直接否掉了：

检查项结果
中转容器是否存在不存在——但不是丢失，是迁移成了宿主机 systemd 服务
api_base 指向已改为新网关，容器内实测 HTTP 200 / 29ms
今日 Switched from（降级到官方）次数0
今日 503 次数0

真正的时间对比（同 provider、同口径）：

指标昨天今天变化
LLM 耗时中位 / p902.64 / 3.32 s2.90 / 3.77 s+10% / +14%
端到端中位（落库到落库）5.71 s5.60 s持平
同窗口 10:00–15:15 端到端5.07 s5.63 s+11%

结论：今天只慢了约一成，不是”显著变慢”。 体感与数据的差距需要另找解释。

2.2 第二次误判：以为上下文膨胀是主因

确实有一个客观变化：今天的输入 token 膨胀了。

指标昨天今天
输入 token p9028,61375,194（+163%）
单次峰值39,23984,307
输入 >40k 的调用次数032

看起来很严重，但拆开 token 构成后结论反转：

构成量级单价
cache 命中部分约 79k近乎免费
未命中部分（uncached）约 5.5k约 24 ms / 1k
输出 token每次几十到几百约 1.8 ms / token

最直接的反证：84k 输入的 TTFT 反而比 47k 输入更低（2.2–3.6 s vs 3.3–4.1 s）。

“上下文变长所以变慢”这个直觉在 KV cache 面前是不成立的。真正按 token 计费的是 uncached 部分和输出，而一次回复里输出多写 40 个字，就吃掉了几千 token 上下文省下的全部时间。

2.3 第三次误判：以为决策 AI 塞了 100 条历史

决策 AI 负责判断”这条消息要不要回”，它的 prompt 实测 16,738 token，比主生成还大。我据此推断”这里面有 100 条历史，砍到 25 条能省 0.3 秒”，并写进了待办。

三条硬证据把这个前提推翻了：

证据一：决策 AI 传的是空上下文

证据二：构造上下文时就跳过了历史

证据三：模型自己的 reasoning 在抱怨

真实日志原文：

“历史消息未提供（只显示这是新消息，之前历史已处理）”
“实际上只有当前消息，没有历史消息内容“

随后 token 数据直接证伪：

时间prompt_tokenscache_hitcache_miss
18:1417,03316,128905
18:2017,02816,256772
18:2516,64316,256387
18:3116,64116,256385

97.6% 是稳定的静态前缀。如果里面真有 100 条历史，每轮都会有大幅波动。

真实构成是：默认判定指令 8,710 字符 + 自定义补充 6,563 字符 + 人格设定 13,431 字符 ≈ 28,704 字符 ≈ 16.2k token。

这条改动最终零改动取消。教训是：看到”prompt 很大”就去猜里面装了什么，不如先看一眼 cache_hit / cache_miss 的比值——静态前缀和动态内容的比例一目了然。

三、真正的原因与修改目的

三次误判清掉后，剩下两个经得起复核的问题。

3.1 问题一：被概率筛掉的消息会永久丢失

插件有一个”概率筛选”机制：不是每条群消息都值得回复，按概率决定处理与否。未通过的消息会被缓存，等下一次真正回复时一起”转正”落库。

问题在于，这条链路上有三处会静默丢数据：

通道机制量级
TTL 过期内存缓存 1800 秒，超时直接丢弃24h 内 362 条进入缓存
条数挤掉上限 10 条，顶格后删最旧日志反复出现”共10条”
进程重启缓存纯内存、不落盘当天重启 14 次

事故实证：17:09:35 一条消息进入缓存，17:39:35 到期，之后再无真实回复把它转正——数据库、JSON、内存缓存三处皆无，永久消失。

数据流转与丢弃点如下：

flowchart LR
    A["群消息入站"] --> B{"概率筛选"}
    B -->|"通过"| C["决策 AI 判定"]
    B -->|"未通过"| D["内存缓存<br/>TTL 1800s / 上限 10 条"]
    C -->|"要回"| E["生成回复"]
    C -->|"不回"| D
    E --> F["落库 platform_message_history"]
    D -->|"下一次真实回复"| F
    D -->|"TTL 到期"| G["永久丢失"]
    D -->|"条数顶格"| G
    D -->|"进程重启"| G

3.2 问题二：关键路径上有一次 4 秒的同步等待

LivelyState 插件里有个”观察者”（GlobalObserver），负责给 bot 提供跨会话的短期氛围摘要——不是事实记忆，是”最近群里在聊什么、氛围如何”。机制是每攒满 20 条消息，调一次 LLM 把 20 条压成一段摘要，下一轮注进 prompt。

它被放在 on_llm_request 钩子里，同步 await：

指标数值
单次摘要耗时中位 4.41 s，p90 7.09 s
命中频率约每 10 轮请求一次

一轮命中的真实时间线：

该轮用户可见延迟 9.3 秒，其中 4.92 秒（53%）花在等这段摘要。 期间 bot 没有任何用户可见输出。

讽刺的是，同一个插件里 judge_dialogue_event 早就用 asyncio.create_task 异步化了，代码注释写得明明白白：

“为什么不放 on_llm_request：那会串行阻塞 1.5 秒。…放 on_llm_response 并用 create_task，回复立即发出…代价是状态延迟一轮生效，对状态系统可接受。”

同样的取舍对观察者完全成立，但作者没在观察者上做。

3.3 本次目的

目的目标
止血被概率筛掉的消息不再因 TTL 而过期丢失
提速把摘要 LLM 移出用户可见路径，降低 p90 延迟
不误伤不动人格设定、不动主生成上下文窗口、不做未经证实的优化

四、修改方式与方案评估

4.1 消息丢失：六个方案的对比

问题不难，难在选哪个改法。候选方案与评估：

方案改动量影响面风险是否解决永久丢失
① 概率筛掉时立即落库~15 行仅覆盖 1/4 缓存入口高：落库无去重，后续转正会重复插入部分
② 延长 TTL 到 7200s0 行（配置）内存几乎不增低否：把”过期丢”换成”顶格挤掉”，更隐蔽
③ 新增定时任务转正~30 行覆盖全部入口中：与原计时器抢同一会话是
④ 落库打”未回复”标记~10 行会污染 prompt 文本或 sender 昵称高：已写入的标记无法清理是（代价不可接受）
⑤ 缓存落盘 + 启动恢复~60 行只解决”重启丢”中否：不对症
⑥ TTL 兜底转正（选中）~15 行 + 1 行配置覆盖全部入口低：复用现成通道是

选中方案⑥的关键，是先发现了一个事实：这条落库通道早就写好了，只是开关从没打开过。

插件自带 _idle_flush_worker → _do_idle_flush → flush_cached_messages_by_params，一条完整的不依赖回复的落库链路，写 conversations → platform_message_history → JSON 三处。但 enable_idle_cache_flush 配的是 false，24 小时日志里触发次数为 0。

更微妙的是：只打开开关还不够。那段计时是固定 600 秒静默，而每条新消息都会 cancel 重建它——活跃群里消息间隔小于 600 秒，计时器永远等不到到期。

所以最终是两处改动：

改动 A（配置，1 行）：enable_idle_cache_flush: false → true

改动 B（源码，约 15 行）：把计时收窄到「最老缓存消息到期前 60 秒」

为什么这个方案风险最低：写入仍走 _do_idle_flush 原有函数，与正常回复转正同一条路径、同一套字段顺序。方案①会引入”即时落库”和”转正落库”两套时序，还要额外负责去重；方案⑥没有第二套语义。

4.2 观察者异步化：三个必须堵的坑

把 if await self._trigger_summarization(...) 改成 asyncio.create_task 看起来是一行的事，实际上有三个坑，任何一个漏掉都会引入新 bug：

坑后果处理
计数不清零原逻辑 new_message_count = 0 在 await 返回后才执行；异步化后任务不再回写，会每轮都触发清零提到派发之前
任务无引用create_task 裸调，任务可能在运行中被 GC 回收实例集合持强引用，add_done_callback 里 discard
并发重入两次摘要竞态覆盖共享状态，且重复消耗额度_summary_inflight 布尔闸门，in-flight 期间不派发

最终改动：

_trigger_summarization 的函数体一字未改——只改调用方式，不改业务逻辑。

需要接受的代价：摘要结果晚一轮请求才可见。这跟作者在 judge_dialogue_event 上已经接受的代价是同一个。

4.3 为什么不动决策 AI

前面 2.3 已经证明”砍历史”无从下手。那还能不能优化决策 AI 的 1.93 秒？

日志里有个此前没人注意的细节：

67% 判”不回复”的调用，每次都先吐 100–220 个 reasoning token 才说出 no。

理论上可以换掉 reasoning 开关，但：

  • 决策质量直接决定”该回不回 / 不该回乱回”，属行为变更
  • 16.2k 里 97.6% 走 cache，砍静态 prompt 对墙钟时间几乎无影响
  • 需要 A/B 才能确认判定准确率不掉

结论：本次不动。 宁可少省 0.3–0.8 秒，也不拿回复质量冒险。

5.2 尚未验证的部分

诚实记录两点：

  1. 冷群兜底转正还没有真实触发过。 它需要群里出现一条”不会被回复”的消息，观察窗口最长 min(600, 1800−60) 秒。
  2. 那个成功日志被 if self.debug_mode: 挡着，而当前 debug 未开启——即使生效也不会打印。验证只能查数据库 B 族是否新增行，看日志会误判成”没生效”。

这个细节值得单独记一笔：验证手段本身可能失效，比功能失效更难发现。

5.3 没被采纳的优化方向

排查过程中还评估过几项，结论都是”收益不匹配复杂度”：

方向理论收益不做的理由
决策 AI ∥ 主生成（投机并行）省 1.93 s67% 的生成白跑；未发送的 assistant 消息会污染历史；额度近乎翻倍
多图转文字并发(n−1)×4.7 s24h 只出现 1 次真实调用，低频
KB 与记忆召回 embedding 去重0.16 s需要跨插件加缓存层，改动 ~30 行
停止截断历史条数 50 → 30省 0.05 s收益小于测量噪声（残差 sd 0.38 s），代价是记忆窗口从 117 分钟砍到 20 分钟

六、复盘

6.1 三条经验

第一，体感和数据要分开记账。 “显著变慢”是体感，7%–13% 是数据。差异本身是线索——它说明真正的痛点不在平均值，而在长尾（p90 上升、偶尔出现 12 秒的回复）。

第二，cache 改变了成本结构。 在 KV cache 面前，”上下文越长越慢”不成立。判断成本要看 cache_hit / cache_miss 比例，以及输出 token 数。

第三，改之前先验证前提。 三次误判里有两次是”假设未验证就写进方案”。如果按”砍决策 prompt 历史”去改，会浪费一整个改动周期，且改完发现根本没生效。

6.2 一处值得记住的反直觉

排查过程中有一个细节反复出现：已有的机制往往只是没打开。

冷群转正通道写得很完整——计时器、worker、三处落库、异常处理全都在，配置项甚至在提示里写着”建议设置为小于等于缓存消息过期时间的值，否则缓存会在转正前就过期丢失”。而它一直是 false。

所以遇到”数据会丢”这类问题时，先检查有没有现成但未启用的通道，比新写一条并行通道更省事，也更不容易引入第二套语义。
